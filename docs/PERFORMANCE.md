# Performance and operating bounds

The first recorded [JMH baseline](benchmarks/2026-11-16/README.md) covers 56 cases on Java 25, with raw samples, allocation profiling, exact workload sizes, and a source identity. It separates compilation, native-tree construction, existing-tree evaluation, serialization, and complete response processing. [Benchmark commands and methodology](../benchmarks/README.md) are maintained alongside the code.

The recorded benchmarks predate the CATNAP dialect and default change. Their field-selection measurements do not establish the cost of RSQL-subset predicate compilation or array filtering. Predicates use the same configurable compilation and evaluation bounds; include their comparisons, membership lists, and array sizes when measuring an application's workload.

On the recorded development machine, the 156-byte small-document projection pipeline averaged 2.035 µs; the 654,251-byte, 4,096-element array averaged 4.612 ms. Evaluating the already constructed trees averaged 0.323 µs and 1.394 ms respectively. These are local CPU measurements without HTTP transport or request binding, not response latency promises.

A 1,045-byte stream record with full-field selection averaged 4.443 µs to prepare, allocating about 24.27 KiB per record. The 65,557-byte record averaged 217.299 µs and about 1,011.48 KiB allocated. The full-field cases preserve wire size, so their costs cannot be attributed to removing fields. See the baseline for native/bypass comparisons and confidence intervals. Allocated bytes are total temporary allocations during an operation; they are not peak or retained heap.

## Initial operating choices

These measurements support keeping limits and query reuse explicit. They do not establish one optimal setting for all applications. The current defaults remain initial guardrails; the measured workloads do not justify raising payload or concurrency bounds for arbitrary applications.

| Setting or choice | Current behavior | Measurement implication |
|---|---|---|
| Compiled-query reuse | Immutable queries; optional HTTP cache of 256 successful queries | Reuse avoids parser/AST allocation. The measured hot key took about 9 ns and 24 allocated bytes per lookup; uncached workload queries took 0.116–3.030 µs. Those are single-thread hot-key results, not a cache-contention model or proof that 256 is optimal. |
| JSON payload byte bound | 1 MiB input and selected output for explicit bounded paths | The 639 KiB array allocated about 15.49 MiB across the complete operation. A byte cap is not a heap-size cap. Budget for trees, temporary encoding buffers, concurrent responses, and framework transport buffers. |
| Query bounds | 16,384 UTF-16 units, depth 64, 4,096 selectors | These bound compilation input and AST complexity. Benchmarking a short query is not a reason to remove the limits. |
| Evaluation bounds | Depth 128 and 1,000,000 work units per document/item | Work is a structural counter, not elapsed time. Large arrays and wide objects have meaningful traversal/allocation cost even with a reusable plan. |
| Sparse field selection | Removes object fields while retaining array shape unless a CATNAP predicate explicitly filters items | A 512-member input projected to 23 bytes, but parsing/serializing the native input still cost work. Tiny output does not imply a cheap response. |
| Streaming execution | Per-item projection with adapter-specific send/demand and scheduling boundaries | Larger records occupy the executing thread longer. Measure the actual endpoint before choosing bounded source scheduling/offloading; do not add an unbounded queue to hide CPU cost. |

Keep application serialization authoritative. Native token/tree conversion can avoid an encoded-JSON round trip in standalone bindings, but an HTTP adapter may need bounded writer capture to retain the selected converter's generic type, view, and custom writer behavior. The isolated-stage results are not additive and do not justify bypassing those semantics.

## Streaming measurements and recorded investigations

[HTTP evidence](benchmarks/2026-11-16/http/README.md) records all five framework targets: 40 throughput/latency cases and 20 retention cases, including 60-second open-connection checks. The [WebFlux drain investigation](benchmarks/2026-11-16/http/webflux-drain-audit/README.md) preserves an earlier 15-second timeout with no recorded delivered count. Repeated-boundary, held-reader, synchronous-source, and archived-source replay runs pass; the original cause remains unknown and no WebFlux production fix is claimed.

Microbenchmarks do not establish first-item HTTP latency, sustained native-framework throughput, cancellation behavior, or retained memory over a long connection. The separate HTTP runs measure NDJSON and SSE using fixed payload sizes, bounded concurrency, and ordinary framework serialization baselines. Their reported ranges describe the measured workload. The original failed attempt and the passing follow-up diagnostics remain part of the record; none establishes a universal delivery deadline.

The dedicated `benchmarks:streaming-fixture` module supplies a shared demand-aware source, pacing, pause/resume controls, subscription counts, global JVM allocation counters, explicit-GC heap snapshots, and JVM/Netty direct-memory metrics. It is test infrastructure and is not published. Nine source/measurement tests and five incremental protocol-reader tests validate those mechanics. The HTTP smoke runner passes native, bypass, full-field, and sparse paths for both protocols on all five framework servers, including concurrent different queries over the same source and disconnect cleanup. Full-duration results are archived separately; smoke timings are not performance evidence.

The recorded measurements keep connections open across increasing durations, pause production while clients drain, then sample retained heap after an observed collection. Both heap and direct-buffer results must be reported separately. Global allocation counters require the Java 25 measurement JVM and include terminated threads; they remain approximate JVM counters. Do not substitute allocation-per-operation figures for retained-memory evidence.

The [Micronaut investigation](benchmarks/2026-11-16/http/micronaut-reentrancy/README.md) reproduces native direct-memory exhaustion with a synchronous source and resume-before-close cleanup. The adapter now uses a bounded asynchronous handoff with prefetch one before native writing. All six Catnap protocol/query combinations pass the adverse-condition regression (7,733,481 delivered records); native endpoints bypass the helper and retain the framework behavior. The full build, publication consumers, and HTTP smoke checks pass with the change. The refreshed native suite passes all 55 tests. The [refreshed full-duration run](benchmarks/2026-11-16/http/attempt-4-micronaut/summary.json) passes all 12 cases. With this asynchronous source, full-field NDJSON throughput falls from about 182,000 to 52,500 records/second, and SSE from about 172,000 to 49,700. The source plus handoff scheduling cost is part of the measured path; these separate local windows do not establish a universal penalty. The one-item bound is retained. Direct-memory counters stay flat across 5/20/60-second samples, with retained-heap ranges of about 1 MiB.

No hard real-time guarantee or cross-framework performance ranking is claimed. The [native-image checks](NATIVE_IMAGES.md) pass for Quarkus and Micronaut. The [requirement audit](RELEASE_AUDIT.md) records completion of the accepted local implementation criteria and the historical timeout. The [final verification](verification/2026-11-16/release-candidate/README.md) passes without relaxing delivery-count assertions or measurement thresholds.
